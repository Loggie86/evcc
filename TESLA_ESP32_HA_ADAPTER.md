# Tesla Wall Connector Gen3 / ESP32 (Loggie86 fork)

**Current status: code built and unit-tested; charging writes not commissioned.**
The firmware and ESPHome YAML at `<local-esphome-config>/charger.yaml`
remain unchanged. Home Assistant is still the charge decision-maker.

## evcc charger type

`tesla-esp32-ha` (available in the fork's charger registry and templates)

The adapter uses the native Home Assistant OAuth API:

- Reads plugged state from `binary_sensor.charger_vehicle_connected`
- Reads contactor from `binary_sensor.charger_contactor_closed`
- Reads actual current from `sensor.charger_vehicle_current`
- Optionally reads power and energy from Tesla Wall Connector sensors
- Reports minimum charging current **8 A**, maximum **32 A**
- Reports fixed single-phase via PhaseDescriber and PhaseGetter, matching the existing installation
- Requests **8/16/24/32 A**, rounding intermediate values **down**
- Never requests 6 A as an operating tier (the *existing firmware* performs
  its independent 6 A contactor handshake)
- Keeps all physical current regulation, Tesla Modbus meter emulation,
  10-second closed-loop adjustments and Kia startup handling in ESP32 firmware

The default is `control: false`: reads only; write methods fail.

## Commissioning preconditions for writes

Before choosing `control: true` all of the following are required:

1. Explicit evcc↔Home Assistant OAuth approval by a person via the evcc UI.
2. A dedicated HA helper `input_text.evcc_esp32_request`, and an exclusive
   owner `input_select.evcc_esp32_authority` with the value `evcc`.
3. A second, independently armed `input_boolean.evcc_esp32_handover_armed`.
4. A **separately built and tested HA relay** that safely translates the
   evcc request into the *existing* ESP32 8-field command:
   `timestamp,amps,phases,32,voltage,L1,L2,L3`.
5. HA policy publication disabled **as a competing charge authority only
   after cutover**, with its protection/stop logic still enforceable.
6. End-to-end tests with both Kia EV9 and BYD Seal, including plug detection,
   8/16/24/32 A, physical 6 A handshake, Kia slow start, overcurrent, grid
   peaks, loss of connection, stale AlphaESS and an immediate Off request.
7. Explicit rollback to HA control documented and tested.

No existing HA safety rules or ESP firmware changes should be removed.

## How requests are sent after handover

The adapter writes only to the dedicated `input_text` helper via
`input_text.set_value`. It never directly writes the existing
`sensor.alphaess_ev_command`, which is generated by HA.

Payload example (values are illustrative):
`{"seq":1760000000000000000,"timestamp":1760000000,"amps":16}`

- Each command checks the exact owner string and separate arming boolean.
- `Enable(true)` sends a zero-amp barrier first, then accepts a freshly
  staged tier or waits for `MaxCurrent`. It never resumes an old tier.
- `Enable(false)` sends a 0 A request and clears the staged tier.
- Requested charging tiers are renewed every 4 seconds. The HA relay must
  validate the timestamp, sequence, identity and owner and stop if there is
  no fresh lease in **15 seconds**.
- Failed reads or writes cannot be treated as permission to charge. An
  independent HA relay and ESP fail-off mechanism are mandatory.

## Read-only test device sample (NOT ACTIVE)

```yaml
chargers:
  - name: tesla_esp32_staged
    type: tesla-esp32-ha
    uri: http://homeassistant.local:8123
    connected: binary_sensor.charger_vehicle_connected
    contactor: binary_sensor.charger_contactor_closed
    current: sensor.charger_vehicle_current
    power: sensor.charger_power
    energy: sensor.charger_energy
    control: false
```

**Do not attach that device to an evcc loadpoint or enable its control**
until the HA relay and full handover are commissioned. Authorising OAuth
itself is read-only unless a write-enabled device is configured.
